## 목표는 생성량이 아니라 발행 기준

여러 서비스의 테스트 공백을 메울 때마다 같은 확인이 반복됐습니다. 테스트를 어디에 두는지, 가짜 객체를 어디까지 만드는지, 검증 명령이 무엇인지. 저장소마다 답이 달랐습니다.

AI에 테스트 작성을 맡기면 이 반복은 줄어듭니다. 대신 다른 위험이 생깁니다. 의미 없는 assertion, 잘못된 mock, 건드리면 안 되는 파일 수정. 그대로 반영하면 테스트가 늘어난 만큼 신뢰는 줄어듭니다.

그래서 목표를 바꿨습니다. 많이 만드는 것이 아니라, **검증을 통과하지 못한 결과가 저장소 밖으로 나가지 않게 하는 것**입니다.

## 생성과 발행 사이의 여섯 단계

저장소별 경로, scaffold 규칙과 검증 명령을 TOML 계약 파일로 분리했습니다. 그다음 한 덩어리였던 작업을 여섯 단계로 쪼갰습니다.

`변경 영향 분석 → 테스트 초안 → 격리 검증 → AI 보완 → 최종 검증 → draft 발행`

각 단계는 앞 단계의 통과를 전제로만 실행됩니다. AI 보완 단계에도 수정 허용 경로, timeout, rate-limit 재시도와 재검증을 걸었습니다. 검증에 실패하거나 정해진 시간을 넘기면 브랜치를 만들기 전에 멈춥니다.

생성 결과는 임시 worktree에서 먼저 돌렸습니다. 원본 저장소는 통과하기 전까지 아무것도 모릅니다.

## 서로 다른 두 개의 확인 결과

보존된 한 차례 실행에서는 변경 후보 518개 중 실제 대상 1개를 골랐습니다. AI 보완 1/1과 검증 1/1을 통과해 draft 브랜치 발행까지 기록됐습니다.

별도로 한 서비스 전체를 검증했을 때는 CI 성공, 코드 실행 범위 80.7%, 테스트 755개를 확인했습니다. 마지막 확인 기준으로 전체 14개 서비스 중 4개가 목표 범위에 도달했습니다.

## 두 숫자를 합치지 않은 이유

위 두 숫자는 서로 다른 범위입니다. 518개 후보를 다룬 실행과 80.7%를 확인한 서비스 검증을 하나로 합치지 않았습니다.

모든 서비스가 같은 수준에 도달하지 않았고, 테스트 작업 전체를 자동화하지도 않았습니다. 자동 머지나 운영 장애 감소 결과로도 넓히지 않습니다. 내부 저장소와 브랜치 정보는 공개 자료에서 제외했습니다.
