## 반복되는 오답, 반복되는 재작업

모델을 올린 뒤 특정 질문의 오답이 반복해서 접수됐습니다. 문제는 수정 방식이었습니다. 그 질문에 맞춰 답변 규칙만 손보면, 표현이 조금 다른 질문이나 그때까지 잘 답하던 질문이 새로 깨졌습니다.

접수된 오류를 일회성 수정 요청으로 처리하지 않기로 했습니다. 다음 모델 교체나 규칙 변경에서도 같은 입력으로 다시 확인할 수 있어야 했습니다.

## 네 개로 나눈 평가군

한 덩어리로 모으면 무엇이 깨졌는지 알 수 없습니다. 그래서 목적이 다른 질문을 따로 보관했습니다.

| 평가군 | 확인 결과 | 이 평가군이 잡아내는 것 |
| --- | --- | --- |
| 고정 원문 | 44/54 → 54/54 | 실제 접수된 실패 질문이 고쳐졌는가 |
| 의미 변형 | 14/14 | 표현이 달라져도 같은 의도를 처리하는가 |
| 기존 정상 답변 | 8/8 | 이번 수정이 멀쩡하던 동작을 깼는가 |
| direct-router | 16/16 | 질문이 의도한 답변 경로로 갔는가 |

세 번째 줄이 이 작업의 핵심입니다. 무엇을 고쳤는지보다 무엇을 깨뜨리지 않았는지가 다음 변경의 근거가 됩니다.

## 답변 경로와 라우팅 경로의 분리 실행

오답에는 두 가지 원인이 섞여 있었습니다. 답변 규칙이 잘못됐거나, 질문이 애초에 다른 경로로 갔거나. 둘을 한 번에 실행하면 어느 쪽인지 가릴 수 없습니다.

그래서 답변은 백엔드 API에서, 라우팅은 direct-router 경로에서 따로 돌렸습니다. 실패 지점이 바로 좁혀졌습니다. 프롬프트 수정만으로 안정되지 않는 사례는 응답 규칙과 코드 검증으로 옮겼습니다.

질문과 기대 답변, 실패 유형은 한 묶음으로 관리하고 답변 규칙과 평가 입력의 변경 이력을 함께 남겼습니다. 수정할 때마다 같은 범위를 다시 실행하는 절차도 문서로 만들었습니다.

## 이 수치가 말하지 않는 것

확인한 범위는 백엔드 답변 API와 direct-router 경로입니다. 고객 환경에 맞춘 내부 검증환경에서 결과를 확인한 뒤 변경을 반영했습니다.

전체 브라우저 화면의 회귀검증과 고객 운영환경의 장기 결과는 확인하지 않았고, 재발 방지 성과로도 표현하지 않습니다. 고객 질문, 답변 규칙 원문과 내부 주소는 공개 자료에서 제외했습니다.
