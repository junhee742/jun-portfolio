## 고치면 다른 게 깨졌다

고객사가 쓰던 모델이 지원 종료를 앞두고 있어 상위 모델로 올려야 했습니다. 올리고 나자 특정 질문의 오답이 반복해서 접수됐습니다.

대응 방식은 팀에 이미 있었습니다. 접수된 질문을 보고 프롬프트와 응답 규칙을 최소한으로 손본 뒤 확인하는 방식입니다. **SR에서는 이게 원칙에 가깝습니다.** 잘 돌아가던 곳을 뜯어고치지 않고 문제가 난 자리만 바로잡습니다. 저도 한동안 그렇게 했습니다.

다만 코드와 프롬프트는 다르게 움직였습니다. 코드는 한 줄을 고치면 그 줄이 하는 일만 바뀌고, 고쳐졌는지는 한 번 돌려보면 압니다. **프롬프트는 한 문장만 바꿔도 상관없어 보이던 질문의 답이 반대로 나오기도 합니다.** 같은 입력을 넣어도 매번 같은 답이 나오는 것도 아닙니다.

**그래서 프롬프트 수정은 한 번 실행으로 판정할 수 없습니다.** 여러 질문을 여러 번 돌려 확률로 봐야 합니다. 최소 수정이라는 원칙은 그대로인데, 그 수정이 맞았는지 확인하는 비용이 코드와 비교가 되지 않았습니다.

판정을 LLM에 맡기는 방식을 찾은 것이 그래서입니다. 다음 모델 교체나 규칙 변경에서도 같은 입력으로 다시 확인할 수 있어야 했습니다.

## 한 덩어리로 모으면 뭐가 깨졌는지 모른다

목적이 다른 질문을 따로 보관했습니다.

| 평가군 | 확인 결과 | 이 평가군이 잡아내는 것 |
| --- | --- | --- |
| 고정 원문 | 44/54 → 54/54 | 실제 접수된 실패 질문이 고쳐졌는가 |
| 의미 변형 | 14/14 | 표현이 달라져도 같은 의도를 처리하는가 |
| 기존 정상 답변 | 8/8 | 이번 수정이 멀쩡하던 동작을 깼는가 |
| 라우팅 | 16/16 | 질문이 의도한 답변 경로로 갔는가 |

세 번째 줄이 이 작업의 핵심입니다. **무엇을 고쳤는지보다 무엇을 깨뜨리지 않았는지가 다음 변경의 근거가 됩니다.**

## 화면까지 확인할 필요는 없었다

파이프라인은 하나입니다. 질문이 들어오면 라우팅 노드가 정해진 프롬프트로 LLM을 호출해 어느 노드가 처리할지 정하고, 넘겨받은 노드가 자기 작업을 한 뒤, 마지막 생성 노드가 답을 만듭니다.

오답의 원인은 그중 두 군데였습니다. 답변 규칙이 잘못됐거나, 처음부터 다른 노드로 갔거나. **최종 답변만 보면 둘이 갈리지 않습니다.** 답이 이상하다는 것까지는 알아도 규칙 탓인지 경로 탓인지는 결과에 묻힙니다.

그래서 파이프라인을 돌리되 결과만 보지 않았습니다. 실행에는 각 노드가 무엇을 받아 무엇을 내놨는지가 남습니다. 라우팅 노드가 어느 경로를 골랐는지를 최종 답변과 따로 판정했습니다. 평가군에 라우팅이 따로 있는 이유입니다.

처음에는 실제 화면을 띄워 출력을 받는 방식도 만들었습니다. 사용자가 보는 것과 가장 가깝기 때문입니다. 그런데 **회귀검증은 프롬프트를 고칠 때마다 돌려야 하는 도구입니다.** 화면을 거치면 느리고, 화면 쪽 문제로 실패해도 프롬프트가 잘못된 것처럼 보입니다. 확인하려는 것은 AI의 답이지 화면이 아니었습니다.

반복해 돌린 것은 그래서 API 경로였습니다. 화면 검증은 전체를 돌리지 않았습니다.

프롬프트는 런타임 DB에 있어서 저장소 파일이 원본이 아니었습니다. 언제 무엇을 바꿨는지 남기려면 그때그때 스냅샷을 날짜별 파일로 빼내야 했습니다.

## 고객사가 직접 확인하고 받았다

마지막 확인은 고객사 환경과 같이 구성한 사내 모델오피스에서 했습니다. 고객사가 그 환경에서 직접 테스트하고 수용한 뒤에 반영했습니다. 처리 이후 같은 유형의 답변 품질 접수는 확인되지 않았습니다.

확인한 범위는 여기까지입니다. 고객사 운영환경에서 오래 지켜본 결과는 갖고 있지 않습니다.
