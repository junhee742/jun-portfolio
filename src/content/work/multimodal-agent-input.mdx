## 텍스트만 들어온다는 전제

상담 제품에 이미지 첨부를 붙이는 작업이었습니다. 사용자가 화면 캡처를 올리고 그것에 대해 묻는 흐름입니다.

기능 자체는 어렵지 않았습니다. 어려웠던 것은 이미지를 받기 시작하자 **원래 있던 단계들이 텍스트만 들어온다고 가정하고 있었다는 사실**이 드러난 것입니다.

## 이미지만 보낸 메시지가 헛돌았다

사용자가 아무 말 없이 이미지만 보내는 경우가 있습니다. 이때 질문을 어느 경로로 보낼지 정하는 라우팅 단계에 빈 문자열이 전달됐습니다. 내용이 없으니 판단할 것도 없는데, 호출은 그대로 나갔습니다.

라우팅 단계에 이미지가 함께 왔는지를 알려주도록 고쳤습니다. 사소해 보이지만 전제가 바뀐 것입니다. 이전에는 "메시지가 비었다"와 "입력이 없다"가 같은 말이었는데, 첨부가 생기면서 달라졌습니다. **모달리티를 하나 늘리면 빈 입력의 정의가 바뀌고, 그게 가장 먼저 새는 곳이 라우팅이었습니다.**

같은 이유로 첨부가 있으면 본문이 비어도 정상 메시지로 취급하도록 입력 검증을 함께 손봤습니다.

## 이미지 설명이 잘못된 모양으로 넘어갔다

이미지는 먼저 설명 텍스트로 바뀐 뒤 검색 단계로 넘어갑니다. 처음에는 그 설명이 가공되지 않은 JSON 덩어리째 전달됐고, 받는 쪽이 그걸 열어서 해석했습니다.

검색 단계가 파싱까지 맡고 있으면 입력 형식이 바뀔 때마다 검색 로직이 흔들립니다. 설명을 미리 파싱한 문자열 목록으로 바꿔서 넘겼습니다. **판단하는 쪽은 판단된 데이터를 받아야 한다**는 것이 이 변경의 내용입니다. RAG에서 LLM은 후보만 제안하고 코드가 결정하게 나눈 것과 같은 원칙입니다.

이미지를 설명으로 바꿀 때 쓰는 프롬프트도 코드에 박아두지 않고 설정으로 뺐습니다. 설명의 품질이 검색 결과를 좌우하는데, 그걸 바꾸려고 배포를 다시 할 이유가 없었습니다.

## 음성은 데모까지만 갔다

음성 입력은 후보를 비교하고 데모를 만드는 데까지 진행했습니다. 인식 오류율과 비용, 하드웨어 요구, 의존성 충돌을 기준으로 비교했고 API 방식을 골랐습니다.

**거기까지입니다.** 고객이 쓰는 릴리스에 나간 기능이 아니라 가능성을 확인한 단계이고, 인식 정확도나 응답 지연을 잰 값도 남기지 않았습니다. 앞의 이미지 입력은 제품의 에이전트와 검색 경로에 실제로 들어갔다는 점에서 다릅니다.
